# 附件：支持格式、限制与行为说明

> 面向实现者与产品。用户在界面上看到的限制值全部来自 `lib/attachments/limits.ts`，
> 本文的表格是那张表的说明；两者不一致时以代码为准。
>
> 规格依据：`docs/superpowers/specs/2026-09-17-lectern-file-attachments-and-references-spec.md`

---

## 1. 两种「文件」不是一回事

用户在 Lectern 里能加两种东西，它们的图标、标签和行为都必须能区分开：

| | 本地附件 | 工作区引用 |
|---|---|---|
| 来源 | 从电脑选择、粘贴、拖入 | 回形针菜单的「引用项目文件」，或输入 `@path` |
| 存放位置 | Lectern 管理的附件库（blob store），**不进项目 git 工作区** | 就在任务对应的 workspace/worktree 里，不动它 |
| 原文件被移动或删除 | 不影响已发送的消息 | 影响——引用的是一个会变的路径 |
| Agent 怎么读 | 走 `read_attachment` / `search_attachments` 工具读解析结果 | 走 workspace 工具按路径读，文件可能已被自己改过 |
| 展示 | 文件名 + 格式 + 大小 + 状态 | 项目相对路径 |
| 上限 | 每条消息 10 个 | 每条消息 32 个 |

附件上传后**复制**一份，所以「发完消息就把桌面上的文件删掉/改名」不会让消息里的文件失效。
消息历史因此可以完整重放。

## 2. 支持格式与单文件上限

| 类型 | 扩展名 | 上限 | 提取正文 | 定位方式 |
|---|---|---:|---|---|
| PDF | `.pdf` | 25MB | 是 | 页码 |
| Word | `.docx` | 20MB | 是 | 标题层级 + 行号区间（**没有页码**，见 §4） |
| Excel | `.xlsx` | 20MB | 是 | 工作表名 + 单元格范围（如 `Sheet1 A12:F30`） |
| Excel 旧版 | `.xls` | 20MB | **否** | — |
| CSV / TSV | `.csv` `.tsv` | 20MB | 是 | 真实行号 |
| PowerPoint | `.pptx` | 20MB | 是 | 幻灯片序号（**按放映顺序**，见 §4） |
| 文本 / 代码 | 见 §3 | 2MB | 是 | 真实行号 |
| 图片 | `.png` `.jpg` `.jpeg` `.webp` `.gif` | 10MB | 不适用 | 作为视觉模型输入 |

**`.xls` 为什么只保存不提取**：它是 BIFF8 复合文档（OLE2 容器），与 `.xlsx`（ZIP + XML）
完全是两种格式，需要另一套解析器。本期选择**接受并保存文件、明确告知用户另存为 `.xlsx`**，
而不是假装读出来了。

## 4. 定位（locator）：为什么每个格式切得不一样

「定位」指的是模型引用内容时给出的那个位置，用户能自己翻开文件核对。所以每个格式
用的是**用户在那个软件里真正看得见的位置**，而不是解析器内部好算的东西：

- **PDF → 页码。** PDF 有真实页码，每页一节。
- **XLSX → 工作表名 + 非空单元格包围盒。** 不是整行整列，也不是 `A1:ZZ900`——那是噪声。
- **PPTX → 幻灯片序号，按放映顺序。** 文件里 `ppt/slides/slideN.xml` 的 `N` 是**文件编号**；
  用户拖过顺序的演示里，它与放映序号不是一回事。直接用 `N` 会在「第 7 页」的位置显示
  第 3 张的内容。序号取自 `ppt/presentation.xml` 的 `sldIdLst`，拿不到时不假装知道
  （标记为非精确并给警告）。
- **DOCX → 标题层级 + 行号，刻意没有页码。** 分页是 Word 的**渲染期**概念，`.docx`
  文件里根本不存在页码。硬按字号行数倒推出来的「第 4 页」换个字体就变了——给一个用户
  翻过去看不到同一段话的定位，比不给定位更坏。
- **文本 / CSV → 真实行号。** CSV 用真正的引号规则切分：引号内的分隔符与换行属于单元格。

## 5. 全局限制

| 项 | 值 |
|---|---|
| 每条消息最多本地附件 | 10 |
| 每条消息附件总字节 | 50MB |
| 每条消息最多工作区引用 | 32 |
| PDF 最多处理页数 | 300（超出时**保留文件**并提示，不报错） |
| 单文件最大体积 | 见 §2 |
| 未绑定消息的草稿附件保留 | 24 小时 |
| 文档解析时间预算 | 90 秒（PDF 整份）/ 单次请求 2 分钟轮询上限 |

内容提取后的字符数同样受预算约束，不会无界进入模型上下文：大文档只把**清单**（有哪些
附件、各自能按什么定位读）注入上下文，正文由模型按需调用工具取回，每次取回都带定位。

## 6. 状态机与失败分类

附件的状态：`preparing → uploading → processing → ready`，任一环节出错转 `error`。

解析失败归为三类，每一类都**不自动重试**：

| 分类 | 触发 | 用户该做什么 |
|---|---|---|
| `password_protected` | 文件加密（OOXML 的 `EncryptedPackage` 流 / PDF 的加密标记） | 去掉密码后重新添加 |
| `no_extractable_text` | 扫描件、纯图片 PDF、空白文档 | 改用图片形式添加，或提供带文本层的 PDF |
| `corrupted` | 结构损坏、压缩包超限、内容与扩展名对不上 | 文件本身有问题，换个文件 |

**为什么不自动重试**：解析是纯函数，同样的字节重新解析还是同样的失败。自动重试只会让用户
多看到一个停在「解析中」的卡片，然后才失败。

「部分页失败」不算整份失败：提取能读的页，在附件卡上给可展开的解析说明（哪几页没读到、
为什么）。

## 7. 安全边界

- **扩展名不可信。** 判定以服务端内容嗅探为准；扩展名只用于前端早期提示与选择器过滤。
- **解压之前先量体积。** 压缩炸弹防护只读 ZIP 中央目录（零解压）就判定条目数、单条解压
  体积、总量与压缩比，通过后才解压**需要的**条目。OOXML 里的图片、字体、嵌入对象从不
  进内存。
- **文档里的东西不执行。** 公式只取缓存结果、绝不重算；超链接只取显示文本、不取 URL；
  宏与外部引用只做只读计数提示。XML 只做标签级扫描，不解析 DTD、不展开自定义实体、
  不解析外部引用。
- **附件按会话隔离。** 一个项目的附件库装的是该项目所有会话的附件，而执行侧是「一个项目
  一个 runner、轮流服务多个会话」。所以每次取用都按 `sessionId` 校验归属，两条路径
  （HTTP 与执行侧）用的是同一道门。
- **不泄露本地路径。** 上传只记 basename；`C:\Users\…` 与 `/Users/…` 都不会进消息、日志
  或模型上下文。
- **文档正文不是指令。** 附件内容以用户数据的形式提供；`read_attachment` 的返回里明确
  写了这一点。

## 8. 清理策略

- 上传后未绑定到任何消息的附件按 24 小时 TTL 清理。
- 一旦被消息绑定，就跟随该会话的保留策略，不再按 TTL 清理。
- 删除会话时清理没有其他引用的附件与解析产物。
- 相同内容按 SHA-256 去重存储；解析结果（按内容寻址）与其 blob 同生命周期。
- 用户主动移除未发送的附件会立即删除服务端文件，不等 TTL。

## 9. 明确不做的事

- 不支持可执行文件、安装包、磁盘镜像或任意二进制分析。
- 不自动解压 ZIP / RAR / 7z（压缩包本身不在支持格式里）。
- 不做云盘同步或第三方文档账号连接。
- 不把本地文件复制进用户的项目工作区。
- 不保证读取带密码或 DRM 的文档——给明确错误，不试。
- 本期不做音视频转录。
- 扫描件不做 OCR（明确提示改走图片输入，而不是给一份猜出来的文字）。
